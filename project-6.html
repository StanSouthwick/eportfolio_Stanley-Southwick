Project 06

Helsinki-NLP Translation API

Production-ready REST API for translating English into French, German, and Spanish — built on Helsinki-NLP's OPUS-MT transformer models, served via FastAPI, containerised with Docker, and monitored with Prometheus.

Overview

A production-ready translation service that takes English text and translates it into French, German, or Spanish using MarianMT transformer models from Helsinki-NLP's OPUS-MT family on HuggingFace. The API is designed for real-world deployment — not a notebook demo.

Models load lazily on first request per language and are cached in memory for the application lifetime, meaning startup is instant and there's no cold-start penalty after the first translation. CPU-bound inference runs via asyncio.run_in_executor in a thread pool, keeping the async event loop free to accept and route new requests while inference happens in a separate thread.

The architecture separates concerns cleanly: translation logic, input validation, safeguarding, and monitoring each live in dedicated modules. Model weights are downloaded at Docker build time, so containers have zero internet dependency at runtime — fully self-contained and reproducible.

Architecture

The request flow is linear and auditable: Request → FastAPI → Safeguards → Translator → MarianMT (thread pool) → Response. HTTP exceptions (422/400) are raised early by Pydantic validation and safeguard checks before any model inference runs. HuggingFace cache integration ensures models are loaded once and reused.

01 Input Safeguarding
safeguards.py validates all inputs before they reach the model and all outputs before they reach the caller. Input checks include empty string detection and regex-based prompt injection detection — preventing adversarial inputs from reaching the transformer.
02 Translation Engine
translator.py handles model loading and inference. Models are lazily loaded on first request per language pair and cached in memory. Adding a new language is a single-line change — just add the Helsinki-NLP model identifier to the language map. Inference runs in a thread pool via run_in_executor to keep the async event loop non-blocking.
03 FastAPI Service
Five endpoints: /health for liveness checks, /languages to list supported targets, /translate for inference, /evaluate for BLEU scoring against human references, and /metrics for Prometheus scraping. Pydantic v2 schemas enforce request/response contracts.
04 Monitoring & Evaluation
Prometheus metrics are scraped every 15 seconds, exposing request count, latency histograms (enabling p50/p95/p99 calculations), and in-progress request tracking per endpoint. The /evaluate endpoint uses sacrebleu to score translations against human references, enabling continuous quality evaluation in production.
05 Containerisation & CI
Docker and Docker Compose for local and production deployment. Model weights are baked into the image at build time via download_models.py — no runtime downloads, no external dependencies. GitHub Actions CI runs the full test suite on every push.

Design Decisions

Lazy loading with caching over eager loading

Models load on first request per language and stay in memory. Startup is instant, and languages that are never requested never consume resources. In a production multi-language service, this avoids loading all models upfront when only a subset may be used.

Thread pool inference, not blocking the event loop

MarianMT inference is CPU-bound. Running it directly in the async handler would block all other requests. run_in_executor offloads inference to a thread pool, keeping the event loop free for concurrent request handling — critical for production throughput.

Baked model weights at build time

Model weights are downloaded during the Docker build, not at runtime. This makes containers fully self-contained — no internet dependency, no startup latency from downloads, and deterministic behaviour across deployments.

Input safeguarding before inference

All inputs are validated and checked for prompt injection patterns before reaching the transformer. Empty strings, malformed requests, and adversarial inputs are rejected early — safeguarding is a separate module, not scattered across handlers.

Single-line language extensibility

Adding a new target language requires only adding the Helsinki-NLP model identifier to the language map in translator.py. No changes to routing, validation, or any other module — the architecture supports extension without modification.

What I Learned

This project forced a different set of decisions to the network anomaly detector. There's no training pipeline to build — the models are pre-trained transformers — so the engineering challenge shifts entirely to serving infrastructure: how to load large models efficiently, how to handle concurrent requests without blocking, and how to monitor quality continuously in production.

The safeguarding module was particularly instructive. Wrapping a transformer in a REST API means exposing it to arbitrary user input, and the gap between "works in a notebook" and "safe to deploy" is non-trivial. Validating inputs, detecting injection attempts, and checking outputs before they reach the caller are production concerns that rarely appear in academic work but dominate real deployments.

Baking model weights into the Docker image at build time — rather than downloading at startup — was a deliberate choice that makes deployments deterministic and eliminates a class of runtime failures entirely. It's a pattern I'll carry forward.
